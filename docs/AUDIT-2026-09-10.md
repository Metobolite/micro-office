# Security and performance audit — 10 September 2026

The repository changes are implemented and locally tested. No production
deployment, live database migration, live data mutation, invitation delivery, or
real-user request was performed. **The SQL fixes are prepared migrations, not
changes to the live Supabase project.** Deploying this application requires the
matching reviewed migrations.

## Scope and project map

- Clean Git working tree at the start; no applicable `AGENTS.md` was found in the
  project or its parent directories. Existing migrations and documentation were
  read before editing. No dependency versions or lockfile resolutions changed.
- Next.js **16.3.4**, React/React DOM **19.1.0**, Supabase SSR **0.12.1**,
  Supabase JS **2.110.3**, docx-preview **0.4.0**. Node **24.18.0**, npm **12.0.2**
  in this audit. App Router only, with Node Route Handlers, Server Actions,
  request-scoped React caches, and the Next.js session proxy.
- Managed Next.js/Node hosting is documented; the actual production host,
  reverse proxy, WAF, CDN, deployment environment, and logs were not available.
- Google/GitHub OAuth goes through Supabase PKCE and `/auth/callback`. Verified
  claims identify the account; dashboard layouts also fetch the current Auth
  user. An HTTP-only active-team cookie selects a workspace only after checking
  the user's memberships. That cookie is not an authorization grant.
- Browser Supabase clients directly read/write tasks, calendar events, messages,
  file metadata and Storage. RLS is the security boundary for these operations.
  Tasks/events/files/time entries are personal within a team; messages and team
  profiles are shared with team members. Timer operations use database RPCs.
- Invitation Server Actions check owner/admin membership, store a random token's
  SHA-256 hash, and send email through server-only Resend credentials. Acceptance
  must also authorize inside the directly callable database RPC.
- Files are uploaded to owner prefixes, then recorded in `files`. Download URLs
  are short-lived bearer links. Avatars use intentionally public Storage URLs.
  PDF previews use Storage signed URLs; DOCX rendering is lazy-loaded and its
  output is sanitized and placed in a sandboxed, CSP-restricted iframe.
- Chat uses Postgres-change subscriptions. Presence uses private channels and a
  permission RPC. AI summaries are an existing placeholder, with no backend.
  No payment flow, webhook receiver, password login/reset endpoint, arbitrary
  server URL fetcher, raw application SQL executor, or command execution route
  was found.

## Findings and disposition

Locations link to the final code. Historical behavior refers to the original
working tree. “Unverified” means exposure in the live application has **not**
been established; the potential impact explains the priority.

| Priority / status | Evidence and conditions | Impact | Implemented fix / next step |
| --- | --- | --- | --- |
| **High potential — unverified live boundary** | `accept-invitation.ts` called `accept_team_invitation_with_role`, whose SQL and grants were absent. Its RPC is reachable directly through Supabase, bypassing Server Action checks. An unsafe deployed definition could accept another account's invitation, grant elevated roles, or process a token twice. | Unauthorized workspace membership if the missing RPC is insecure. | [Invitation migration](../supabase/migrations/20260910120000_invitation_boundaries.sql) adds `accept_team_invitation_secure`; [action](../app/action/accept-invitation.ts) uses it. It locks the invitation, reads the current confirmed email from `auth.users`, checks expiry/status/role and the inviter's current permissions, serializes membership creation, never elevates existing membership, and consumes the invitation transactionally. Public/anonymous execution is denied; the known legacy `(text)` signature loses client grants. Export and audit other overloads/privileged functions before release. |
| **High potential — unverified live configuration** | No Storage policies were versioned, although browser clients upload, sign, read and delete objects. Database `files` policies do not protect Storage by themselves; a public `user-files` bucket bypasses private read policies. | Disclosure, deletion or replacement of another user's objects if live policies are broad. | [Storage migration](../supabase/migrations/20260910122000_storage_policies.sql) adds restrictive guards over legacy policies, exact owner prefixes, linked-file membership checks, and denies overwrite/move. Owner-only orphan access preserves failed-upload/deletion cleanup. Private-bucket preflight fails closed. Bucket limits and live Storage API behavior still require staging verification. |
| **Medium — confirmed missing control, fixed in prepared SQL** | [Invitation action](../app/action/send-invitation.ts) had no persistent issuance quota. Any authenticated user able to own/create a workspace could call it repeatedly for different recipients. | Unwanted invitation email, delivery costs, and database growth. | The invitation INSERT trigger validates identity/role/token/expiry and atomically maintains private quotas across application instances: **20 successful invitations per actor per UTC hour**, **50 per team per UTC hour**. Direct PostgREST inserts cannot bypass it. Rejections produce a friendly message before email delivery. Fixed windows allow boundary bursts; multiple accounts still need provider/edge abuse controls. |
| **Medium — confirmed resource-limit gap, fixed** | [DocumentPreview](../app/components/document-summaries/DocumentPreview.tsx) checked the stored/compressed 20 MiB file size, then handed the ZIP to JSZip/docx-preview on the browser thread. Small ZIP files can contain much larger XML or lie about expanded size. Users must open an untrusted document; this app does not share another user's private document list. | Excessive browser CPU/memory use or a frozen tab. | [Archive validator](../app/lib/docx-archive.mjs) measures actual decompressed bytes in a [worker](../app/lib/docx-preflight.worker.ts) before the renderer loads. Limits: 1,000 members, 64 MiB total expansion, 16 MiB per binary member, 4 MiB per XML/relationships member. Rejects inconsistent sizes, malformed paths, duplicate names and unsupported/encrypted archives. Cancellation and a 10-second timeout terminate preflight. Complex or unsupported documents remain downloadable. Parsing/rendering below these bounds still costs browser resources. |
| **Medium — confirmed performance and consistency issue, fixed** | [Task reorder handler](../app/components/tasks/TasksPageClient.tsx) used one HTTP update per changed task. A failure triggered compensating updates, which could themselves fail or overwrite concurrent changes. | Request bursts, partially saved task order, and poor responsiveness on large columns. | One bounded [SECURITY INVOKER RPC](../supabase/migrations/20260910121000_atomic_task_reordering.sql) validates the complete batch, locks rows in consistent order, enforces user/team ownership and RLS, and updates transactionally. Unknown fields, duplicate IDs, invalid statuses/orders and inaccessible tasks reject the whole batch. A failed response causes one reconciliation read, without compensating writes. Concurrent valid reorders retain last-writer behavior; collaboration conflict resolution was not added. |
| **Low — confirmed validation issue, fixed** | Membership lookup used an email directly as an `ilike` pattern. Valid email local parts may include `%` or `_`. | An unrelated existing address could incorrectly block an invitation. This is pattern matching, not SQL injection. | [Invitation action](../app/action/send-invitation.ts) escapes wildcard and escape characters while preserving case-insensitive matching. |
| **Low — confirmed validation weakness, fixed** | [Avatar helper](../app/lib/profile-avatar.ts) searched for the Storage endpoint marker anywhere in a URL path and accepted arbitrary final filenames. | Invalid/misleading avatar paths could pass the application ownership guard; actual unauthorized Storage access was not demonstrated. | Require the exact endpoint prefix and origin, no URL credentials, the current user's folder, and a supported image filename. Tests cover another user, another host, fake prefixes and encoded traversal. |
| **Low — confirmed logging exposure surface, reduced** | Invitation/profile/workspace actions logged entire database error objects. PostgreSQL errors can include row values and constraint details. | Private profile/invitation information can enter server logs when an operation fails; no production log disclosure was demonstrated. | Changed these action logs to error codes. Existing client-facing database messages and hosting log retention still deserve operational review. |

## Dependency advisory review

Current official advisory pages and a fresh `npm audit --offline=false --json`
were accessible. The registry audit reported **zero known vulnerabilities**
across 521 resolved dependency entries, before/after with unchanged versions.
This is a scanner result, not proof of security.

- The [Next.js August 25 security release](https://nextjs.org/blog/august-2026-security-release)
  patches the AVIF image-optimizer and Windows mixed-router RCE issues in
  **16.3.3**. Installed **16.3.4** includes those fixes. This application has no
  Pages Router or configured remote image optimizer patterns.
- The [Next.js advisory list](https://github.com/vercel/next.js/security/advisories)
  and [Server Action DoS advisory](https://github.com/vercel/next.js/security/advisories/GHSA-m99w-x7hq-7vfj)
  were reviewed. The current App Router/Server Action paths are relevant, but
  the installed Next release is already patched; no forced upgrade was needed.
- React's [July Server Functions advisory](https://github.com/react/react/security/advisories/GHSA-wx67-qw84-cm4g)
  concerns `react-server-dom-*`, not the plain browser `react` package alone.
  Next.js vendors its RSC implementation; the installed bundled package declares
  the July 31 `19.3.0-canary-cbb046ab-20260731` build. Treating the lockfile's
  plain React 19.1.0 as an independently reachable RSC vulnerability would be
  misleading. Next's patched release is the relevant framework boundary here.

No Next/React major upgrade or automatic dependency fix was performed.

## Other security checks

- Server Actions check identity and role independently of layouts. Workspace
  selection checks membership. Profile updates whitelist fields and bind avatar
  changes to the current account. No mass-assignment action was found.
- Existing table policies are restrictive as well as permissive; the test
  fixture deliberately installs unsafe legacy allow-all policies to verify the
  restrictive guards. Own-resource CRUD and membership bootstrap constraints,
  message sender stamping, and message length limits were exercised.
- SQL uses parameters or fixed migration identifiers. File keyset filters
  validate UUIDs and timestamps before building PostgREST filter syntax. Filenames
  are sanitized. The new RPC accepts only the three intended task fields.
- OAuth redirects are canonicalized to internal routes; callback responses are
  private/no-store and use relative Location headers. Logout requires POST and
  rejects a mismatched Origin. Next Server Actions retain same-origin checks
  and their default request-body limit; no broad CORS allowance was added.
- Session refresh uses Supabase verification. Request-scoped React `cache()` is
  not a shared cross-user cache. Authenticated routes are dynamic and produced
  private/no-store responses in local checks. No public caching was added.
- Active-team cookies use HTTP-only, SameSite=Lax and production Secure flags.
  Supabase browser auth requires access to its session cookies; converting those
  to HTTP-only without changing the auth architecture would break the client.
- Security headers already cover framing, MIME sniffing, referrers, feature
  permissions and production HSTS. The application CSP is partial: it does not
  restrict `script-src`. A nonce-based script policy is a defense-in-depth
  follow-up requiring testing with Next inline scripts, themes and previews.
- React escapes application text and invitation email HTML is escaped. DOCX
  HTML remains isolated in its existing sandbox/CSP. No confirmed application
  script-injection path was found. PDF files and copyable signed links are
  intentionally opened from Storage; MIME validation, private bucket settings
  and signed URL lifetime remain deployment concerns.
- Only `.env.example` is tracked. A limited tracked-file credential-pattern scan
  found no private keys or common secret-token patterns. Build environment
  validation rejects service-role/secret Supabase keys in the browser variable.
  Resend remains server-only. Secret values were not printed. This was not a
  historical Git or production-bundle secret-forensics exercise.

## Performance findings and evidence

| Area | Before | After / disposition |
| --- | --- | --- |
| Task order save | N changed rows generated N separate update requests, plus possible compensating requests. | One RPC for up to 1,000 changes / 256 KiB of JSONB. A synthetic SQL regression updated **500 tasks in one call** and verified all 500 persisted. The 500-versus-1 request count follows from the original and final handlers; it is not a measured network-latency speedup. |
| DOCX preflight | Compressed-size check only; archive inflation happened in the renderer. | A synthetic 5 MiB XML payload compressing below 10 KiB, including a forged low size header in the unit test, is rejected before rendering. Browser tests exercised the built worker with a valid archive and an oversized archive. No INP or memory percentage is claimed. |
| Lists and queries | Files/documents already use 30-row keyset pages; chat loads at most 200; calendar limits queries by date; dashboard cards request four rows. Independent queries already use `Promise.all`/Suspense. | Preserved. No speculative cache or memoization was added. |
| JavaScript | Interactive feature boundaries, dynamic modal imports, on-demand Supabase login import, and dynamic DOCX library import were already present. | Preserved. The validator is emitted in a worker chunk and only started for DOCX preview. No bundle-size reduction is claimed. |
| Fonts/layout | Manrope is downloaded during build and then served locally; images/avatar boxes reserve dimensions. | Preserved font/design. Build required network permission locally; browser home/theme/mobile checks passed without runtime/hydration errors. |

Remaining scale limits: task and membership reads lack explicit pagination and
can hit the configured PostgREST row cap; a complete sortable board needs a
deliberate pagination/search design. Timer history refetches its growing loaded
window every 30 seconds while visible and re-renders the timer component each
second while running. These may affect INP/transfer cost with larger real data;
they were not benchmarked or changed without representative data. No LCP, CLS,
INP, TTFB, p95 latency, or before/after bundle-size improvement is asserted.

## Required review and remaining limitations

1. **Export the actual base schema, policies, function definitions/overloads,
   grants and migration history.** The synthetic fixture is explicitly not a
   production schema. Check column types/defaults/constraints, unique membership
   keys, trigger interactions, migration role privileges, and legacy object paths
   against staging. The unknown settings/presence/timer RPCs can bypass RLS if
   privileged; their authorization is still a high-priority unresolved boundary.
2. Configure and verify bucket privacy, MIME and size limits in staging. Existing
   avatars outside the supported filename/extensions need compatibility review.
   Public avatar reads deliberately remain public. Signed file links remain
   usable until expiry; revoking a membership cannot recall an issued bearer URL.
3. Apply the three new migrations **only after review/testing**, then coordinate
   the matching application release. Invitation acceptance and reordering depend
   on the new RPCs. The old acceptance RPC is revoked, so old application instances
   need a coordinated transition. No automatic live migration is configured.
4. For rollback, retain the old application and export of original grants/policies.
   Stop new RPC callers before removing their functions. Restore the legacy
   acceptance grant only after confirming its authorization; do not blindly
   restore broad Storage policies. Counter tables contain no required user data.
5. Complete real staging OAuth/refresh/logout, team create/select, task drag,
   calendar CRUD, chat/reconnect, avatar and file upload/download/delete,
   PDF/DOCX preview, invitation delivery/acceptance and timer operations with
   separate test accounts. Local SQL tests and unauthenticated browser smoke do
   not establish that these authenticated live integrations work.
6. Inspect Supabase Auth signup/rate-limit/CAPTCHA settings, email delivery
   controls, Realtime authorization/publications and edge request limits. OAuth
   is delegated to Supabase; an in-process Next limiter would not protect direct
   provider calls. Multi-account abuse, chat/storage quotas and large RPC input
   transport limits still need provider/edge controls.
7. Existing delivery failure/expired-pending invitations block reinvitation.
   A transactional resend/expiry workflow remains unimplemented. No new email
   retry was added because duplicate delivery and ambiguous network failures need
   a durable idempotency/outbox design.

This audit improves the inspected code and supplies executable boundary tests.
It does not guarantee the absence of vulnerabilities, validate unprovided live
policies/RPCs, or replace authenticated staging and production configuration review.
